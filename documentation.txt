INTRODUCTION
LAN-Caster is a peer-to-peer file transfer tool for local networks written in
Java 17 + JavaFX. This document explains the architecture introduced in
version 2.0 (push-style transfers with accept dialogs, parallel block streaming,
resume support) and every class in the codebase.

1. EXECUTIVE SUMMARY
- Every running instance listens on one TCP port (5000, or the next free port)
  and announces itself over UDP every 2 seconds.
- Devices must be PAIRED once before they can exchange files. Pairing shows a
  6-digit code on the requesting device; the other device shows the same code
  and the user presses Pair. Both sides remember each other (paired.<id> in
  config). Offers from unpaired devices are rejected automatically.
- Sending is a push: the sender picks paired devices and files, connects to
  each device and OFFERS the file. The receiver sees a card with Accept /
  Save to… / Decline. Nothing is transferred until the receiver accepts, and
  both sides see exactly what state the transfer is in (Waiting, Receiving,
  Completed, Failed with reason …).
- Once accepted, the sender pushes the file as 16 MB blocks over N parallel
  TCP streams (N chosen by the receiver, default 2–6 depending on CPU count)
  using zero-copy FileChannel.transferTo. The receiver reads with 4 MB direct
  buffers and positional FileChannel writes, so streams never contend on a
  file position.
- Every received block is recorded in a bitmap stored next to the partial
  file. A cancelled or interrupted transfer resumes where it stopped when the
  same file is offered again (works across app restarts). This makes 100 GB
  transfers practical.

3. HOW A TRANSFER WORKS
  Pairing (once per pair of devices)
  Sender (A)                                   Receiver (B)
  user clicks unpaired device B
  connect B:port ---- PAIR id,name,code ---->   dialog "A wants to pair, code 123456"
  dialog "confirm code 123456 on B"             user presses Pair
                 <------ PAIR_OK id,name -----  B stores paired.A
  A stores paired.B

  File transfer
  Sender (A)                                   Receiver (B)
  ----------                                   ------------
  user selects B + file
  connect B:port ----------- OFFER ---------->  card "A wants to send X" appears
  card "Waiting for B to accept"                user clicks Accept
                <--- ACCEPT streams, ranges --  (ranges = blocks B still needs)
  open N data connections -- DATA id,i ------>  OK
  push blocks [hdr][bytes] ... ------------->   write at offset, mark block
  end marker on each stream
  card "Finishing"               <---- DONE --  rename .lcpart -> final name
  card "Completed"                              card "Completed · Open folder"

  Either side can send CANCEL / ERROR on the control connection at any time.
  The receiver keeps the .lcpart and .lcstate files after a cancel/failure so
  the next OFFER of the same file resumes (only the missing ranges are sent).

4. WIRE PROTOCOL (see Protocol.java)
Every connection starts with: UTF "LANC", int version(2), UTF kind.
kind = OFFER : Offer payload (transferId, fileName, fileSize, senderName,
               senderId, blockSize, lastModified). Reply:
               ACCEPT int streams, int n, n × (long start, long length)
               DECLINE UTF reason
               Then status messages both ways: DONE | CANCEL reason | ERROR reason
kind = DATA  : UTF transferId, int streamIndex. Reply OK or ERROR reason.
               Then blocks: 12-byte header [long offset][int length] + bytes.
               Header offset = -1 ends the stream.
kind = PING  : reply PONG, id, name, os, int version (used by "Add by IP").
kind = PAIR  : UTF senderId, UTF senderName, UTF code, int senderPort.
               Reply PAIR_OK id name (after the user confirms) or DECLINE reason.
               An OFFER from an id that is not in the paired list is answered
               with DECLINE before any session is created.
All multi-byte numbers are big-endian (DataOutputStream).

5. CLASS REFERENCE
5.1 TransferEngine (core/transfer)
  - start(): binds PeerServer (port 5000 or a free port), starts the 1 s watchdog.
  - sendFile(File, PeerInfo) / sendFiles(...): creates a TransferSession in
    state CONNECTING and runs an OutgoingTransfer on the IO pool.
  - onOffer(...) (PeerServer.Handler): reads the Offer, creates a session in
    state INCOMING_OFFER, notifies the UI, runs IncomingTransfer.runControl()
    on the server thread.
  - onData(...): routes a data stream to its IncomingTransfer.
  - ping(ip, port): identifies a device added manually.
  - requestPairing(peer, onCode) / onPair(...): the pairing handshake; the UI
    supplies a pairingHandler that asks the user to confirm the code.
  - setUnpairedOfferListener: lets the UI explain why an offer was rejected.
  - watchdog(): fails transfers that made no progress for 60 s and flushes
    resume state to disk.
  - setSessionCreatedListener: how the UI learns about new sessions.

5.2 TransferSession
  Observable model shared by engine and UI: id, direction, fileName, fileSize,
  peer name/ip/port, state (INCOMING_OFFER, CONNECTING, WAITING_ACCEPT,
  TRANSFERRING, FINALIZING, COMPLETED, FAILED, CANCELLED, DECLINED), message,
  bytesDone (AtomicLong), SpeedMeter, streams, resumed flag, localFile.
  accept(dir)/decline() complete the receiver's decision future;
  requestCancel() calls the engine-provided canceller. State changes notify
  listeners; byte counters are polled by the UI timer (300 ms).

5.3 OutgoingTransfer
  run(): control connection, OFFER, wait for ACCEPT (up to 3 min), build the
  block queue from the missing ranges, start N stream workers, wait for DONE.
  streamLoop(): one TCP connection; takes blocks from the shared queue, writes
  header + FileChannel.transferTo (4 MB pieces for smooth progress), retries a
  failed connection up to 3 times and re-queues its block. After all streams
  finish, up to 2 extra single-stream rounds drain any re-queued blocks.
  cancel()/fail(): send CANCEL/ERROR, close all channels.

5.4 IncomingTransfer
  runControl(): waits for the user's decision (or auto-accept), prepares the
  file (sanitised name, <name>.lcpart preallocated with setLength, loads
  <name>.lcstate if it matches size/blockSize/lastModified), replies ACCEPT
  with the missing ranges, then reads status messages until the transfer ends.
  attachStream(): reads block headers and bytes into a 4 MB direct buffer and
  writes them with fc.write(buf, position); marks blocks in ResumeState; the
  stream that completes the last block calls finish().
  finish(): force(), close, rename .lcpart to the final name (adds " (1)" if
  the name exists), delete .lcstate, send DONE.
  cancel()/fail(): keep partial files, save state, notify the sender.

5.5 ResumeState
  BitSet of received blocks; missingRanges() returns contiguous {start,len}
  pairs; save() writes a properties file atomically (temp + move).

5.6 PeerServer (core/network)
  ServerSocketChannel with SO_RCVBUF set before bind (so TCP window scaling
  applies). Accept loop hands each SocketChannel to the pool; handle() does
  the handshake with a 15 s timeout and dispatches OFFER/DATA/PING.

5.7 DiscoveryService (core/discovery)
  Listens on UDP 8888 (bound to 0.0.0.0 with SO_REUSEADDR, joins
  239.255.77.77 on every eligible interface). Announces every 2 s on every
  interface: a multicast datagram pinned to that interface plus a subnet
  broadcast as fallback. Packet: LAN-CASTER_HELLO|id|base64name|port|os|ver.

5.8 PeerInfo
  id (persistent instance id), ip, port, name, os, protocolVersion, lastSeen,
  manual flag. Online = seen in the last 10 s; removed after 60 s silence.
  Equality by id (or ip:port for manual peers).

5.9 Config (core/util)
  device.name, instance.id, peer.<ip> names, paired.<instanceId> = name,
  download.dir, transfer.streams (0 = auto), transfer.autoaccept.
  System properties for testing two instances on one PC:
  -Dlancaster.configDir -Dlancaster.instanceId -Dlancaster.deviceName
  -Dlancaster.autoAccept -Dlancaster.downloadDir

5.10 NetworkUtils
  eligibleInterfaces(): up, non-loopback, multicast-capable, has IPv4;
  physical adapters first, Docker/VPN style adapters last.
  broadcastAddresses(), localIPv4Addresses(), osTag().

5.11 MainWindow (ui)
  Decorated, resizable window. Left: device list; unpaired devices show a
  "Pair" chip (click to pair), paired devices show a checkbox; online dots,
  right-click Pair/Unpair / Rename / Copy IP / Remove, "Add by IP". Right: stats
  (active, current speed, completed), big "Send files to N devices" button,
  drag & drop onto the window, transfer cards. Toast notifications replace
  modal pop-ups. Settings: download folder, parallel streams, auto-accept.
  A 300 ms Timeline refreshes progress/speed/ETA and expires silent peers.

5.12 TransferCard
  Renders one TransferSession; rebuilds its buttons only when the state
  changes (Accept/Save to…/Decline, Cancel, Retry, Open folder, Dismiss).

6. CHUNKING, PARALLELISM, RESUMABILITY
- Block size 16 MB: small enough that a lost connection wastes little, large
  enough that per-block overhead (12 byte header, bitmap update) is nil.
- Work queue instead of fixed ranges: streams pull the next block from a
  shared queue, so a slow stream never leaves the others idle (no tail
  latency at the end of the transfer) and disk reads stay roughly sequential.
- Sender: FileChannel.transferTo = sendfile on Linux / TransmitFile on
  Windows; file bytes never enter the Java heap.
- Receiver: SocketChannel.read into a direct buffer + positional write. The
  previous implementation used FileChannel.transferFrom, which internally
  reads 8 KB at a time; direct 4 MB reads are several times faster.
- Socket buffers 4 MB set before connect/bind; TCP_NODELAY on.
- Resume: .lcstate bitmap saved every second by the watchdog and on
  cancel/failure; preallocated .lcpart keeps the final size.

7. DISCOVERY
See 5.7. Why both multicast and broadcast: Wi-Fi access points and some
switches drop or rate-limit multicast; Linux hosts without a default route
cannot send to a multicast group unless the socket is pinned to an
interface. Sending on every interface fixes machines with Docker/VPN
adapters. If discovery still fails, "Add by IP" uses a direct PING.

8. PACKAGING (CONVEYOR) AND THE LINUX FIX
Root cause of the broken Linux build: conveyor.conf added target/lib/*.jar
to the inputs. Maven only downloads the JavaFX jars for the build machine
(javafx-*-win.jar), so the Linux .deb / .tar.gz shipped Windows natives and
no libglass.so / libprism*.so. conveyor.conf now uses
  include required("/stdlib/jvm/javafx/from-jmods.conf")
  javafx.version = 21.0.6
  app.jvm.modules += javafx.controls
which downloads the JavaFX jmods for each target OS and links them into the
runtime; only the application jar is an input.
Build: mvn package  →  conveyor make site

Firewall note: receivers must allow inbound TCP 5000 (or the port shown in
the header) and UDP 8888. Fedora/openSUSE (firewalld) block these by default:
  sudo firewall-cmd --add-port=5000/tcp --add-port=8888/udp --permanent
  sudo firewall-cmd --reload

9. PERFORMANCE NOTES
- Gigabit Ethernet: expect ~110 MB/s with 2–4 streams; the disk is usually
  the limit for HDD targets.
- Wi-Fi: fewer streams (2–3) are often better; configurable in Settings.
- 2.5/10 GbE: raise streams to 8–12 and use SSDs on both ends.
- Loopback test on the dev machine: 300 MB in 1.8 s (≈170 MB/s, disk-bound).

10. TESTING
LoopbackTransferTest starts two engines on localhost, checks that an unpaired
sender is declined and that pairing needs confirmation, transfers a 300 MB
pseudo-random file and verifies the SHA-256, then cancels a transfer at 30 %
and verifies that the second attempt resumes and the final hash matches.
Run with: mvn test
